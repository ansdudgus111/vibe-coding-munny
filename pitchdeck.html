나이브 베이스라인

한 줄씩 다섯 번 던졌고, 그때마다 AI가 혼자 정한 것

실제로 던진 프롬프트 (원문 그대로)
1턴

대학생용 투두리스트 앱 만들어줘

2턴

심리적으로 번아웃이 온 학생에게 힐링을 줄만한 요소를 추가해줘

3턴

힐링컨셉의 ui로 만들어줘

5턴

어떻게 해야 투두리스트의 존재를 잊지 않고 할일을 완료할 수 있을지 방법을 생각해봐

AI가 혼자 정한 것 3가지
  • 분류(학업/개인/동아리)·우선순위 필드 — 요청에 없었음
  • "방법을 생각해봐"(3턴 아이디어 요청) → 되묻지 않고 알림·연속 기록·등급 시스템을 전부 완성된 기능으로 구현
  • "힐링 컨셉"을 분위기가 아니라 제목 속 단어("힐링 투두리스트")로 그대로 처리

문제가 됨

아이디어를 물었는데 완성 기능을 만들어버림 — 질문과 구현을 구분하지 못했다

문제가 안 됨

분류·우선순위, "힐링" 단어 삽입은 범위 밖이었지만 작동에는 지장이 없어 쉽게 들어냈다

AI가 스스로 만든 화면
느낀 점
프롬프트 속 단어를 그대로 받아들이는 경향이 있다. "힐링 컨셉"이라고 하면 "힐링"이라는 단어 자체를 프로젝트 이름에 넣는 식이다. 화면 구성도 요청이 들어온 순서대로 위에서부터 쌓아 올린 느낌이라, 버튼과 요소의 배치 흐름이 매끄럽지 않았다.
의사결정 사례 1
● 개입함

막연한 요청 대신, 내 상황을 넣어서 출발점을 직접 정했다

상황

맨 처음부터 "할 일 관리 앱 만들어줘"처럼 막연하게 묻지 않았다. 이번 학기 겪은 번아웃 경험을 구체적으로 설명해서, AI가 잡을 방향 자체를 처음부터 좁혔다.

실제로 쓴 시작 프롬프트

나는 내가 해야되는 일을 시각적으로 보여주고 목표를 설정하면 팝업으로 지속적으로 알려주는 걸 만들고 싶거든 내가 이번학기 번아웃이 와서 스크린 타임은 느는데 할 일은 똑바로 안 됐거든 그래서 그런걸 좀 힐링하고 고치기 위해서 가시적으로 할일을 할 수 있도록 도와주고 힐링할 수 있는 앱을 만들고 싶어

만약 막연하게만 물었다면

슬라이드 3의 결과

기분 체크 이모지, "힐링"이라는 단어를 제목에 그대로 삽입 — 피상적인 "힐링"

내 페르소나를 넣은 결과

"별사탕이 병에 차오른다"는 구체적인 비유 — 번아웃 경험(할 일은 안 되는데 화면만 들여다봄)에서 나온 방향

판단 · 결과

개입함 — 일반적인 요청을 던지면 AI가 또 피상적인 "힐링 키워드"로 받아칠 거라고 보고, 처음부터 내 상황을 구체적으로 넣어 방향을 좁혔다. 이 설명이 이후 "단계 체크 → 병이 차오름"이라는 핵심 기능의 뼈대가 됐다.

의사결정 사례 2
● 개입함

무드 레퍼런스를 모았지만, 저작권 있는 것은 그대로 쓰지 않았다

상황

앱의 분위기를 정하려고 손그림 스티커, 폰트 샘플 같은 레퍼런스 이미지를 모아서 전달했다.

AI가 한 일

문제

폰트 레퍼런스("Curly Story")는 상업용 폰트라 이 Public 저장소에 그대로 쓰면 라이선스 위반

대체

오픈 라이선스(OFL) 폰트 "Send Flowers"의 글자 윤곽선으로 로고를 다시 그리고, 소용돌이·별·꽃은 직접 벡터로 그렸다

판단 · 결과

개입함 — 느낌만 참고하고 실제 폰트·이미지는 쓰지 않았다. 저장소가 Public이라 라이선스 문제는 그대로 드러난다. 지금 로고(wordmark)와 병 속 둥근 별 모양이 그 결과다.

의사결정 사례 3
● 개입하지 않음

기준 문서를 만들어 AI에게 맡기고, 그 안에서 나온 판단은 받아들였다

상황

CLAUDE.md라는 기준 문서를 만들어 AI에게 이 프로젝트의 "역할"을 주고, 이후 모든 요청을 이 문서 기준으로 판단하게 했다.

사례 A — 대안에서 타협점 찾기

네가 이 프로젝트의 교수라고 생각하고 단점과 해결책을 고민해봐 → 그렇게 수정해줘

새 화면을 추가하면 "화면 3개 이하" 규칙을 어기는 상황에서, AI가 그 규칙을 스스로 짚고 목록 화면 안 펼침 패널 대안을 냈다. 더 나은 방법이 없어 그대로 받아들였다.

사례 B — 내가 놓친 채점 기준을 AI가 짚음

과제 채점 기준을 화면 캡처만 보고 판단했는데, AI가 실제 README 원문을 다시 확인해보자고 해서 대조해보니 커밋 해시 같은 검증 가능한 증거가 요구된다는 걸 놓치고 있었다. 그 뒤로 커밋 단위 작업과 기록을 더 꼼꼼히 남기는 쪽으로 방향을 수정했다.

판단 · 결과

개입하지 않음 — 기준 문서 안에서 나온 제안과 교정은 그대로 받아들였다. 문서를 미리 만들어 둔 덕에 AI가 매번 같은 기준으로 판단할 수 있었다. 화면은 3개로 유지됐고, 제출 준비는 증거 중심으로 바뀌었다.

결론

코드는 AI가, 방향과 확인은 사람이

AI가 믿을 만했던 영역

구현 과정에서 코드 문법을 다루는 부분은 AI에게 맡기는 게 편했다. 문법 오류를 잡거나 반복적인 코드를 쓰는 작업은 빠르고 정확했다.

사람이 꼭 필요했던 영역

① 정확히 어떤 앱을 만들고 싶은지 끌어내는 과정
② 웹·모바일 화면에서 실제로 보이는 UI가 일관된지 확인하는 과정

구체적인 기능과 구조를 정하는 데는 사람의 판단이 계속 필요했다.

다음 프로젝트에서 다르게 할 것

"AI가 아무것도 모르는 상태"가 필요한 작업(나이브 베이스라인 같은)은 같은 세션 안에서 폴더만 분리하거나 서브에이전트로 흉내 내도 소용없다. 처음부터 완전히 새로운 세션으로 시작해야 한다.
